# Rubric: is this reproduction package ready to post?

<!--

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (wherever the report states versions and platform), read against the issue's own environment lines and the `bug reports` template line in the repo facts | Pass when the report states (a) the operating system and (b) the project's version, commit, or build, AND (c) any component the issue or thread names as part of the trigger (the driver, the shell, the browser and its language order, the build profile, a decisive dependency version) when the issue's behavior depends on it. Install method and extra detail are welcome but not needed; a one-line record carrying (a), (b), and (c) passes. Fail when the OS or the project version is missing, or a trigger-deciding component the issue names is missing. "Windows 11" with no project version fails; a report with no environment record at all fails even when its artifact is perfect. | required |
| steps-rerunnable | The repro report's steps, commands, inputs, and configuration, read against the issue's steps to reproduce | Pass when a stranger with the same environment could go from a stated starting state to the trigger using only the report plus the issue: every command is given as run, every input file or config is shown or described exactly enough to recreate (quoting the issue's exact text, running "the issue's script verbatim", or naming the one distinguishing content of a minimal file such as "a valid dependencies list plus a category section" all count), and every resource used is obtainable by the reader. Interactive steps written as key presses or UI actions count as steps. Fail when any step depends on something the reader cannot get (a private repository, an unshared config or block list, "our internal setup"), when a step is generic with no command or action ("set up the project", "ran the reproduction"), when a step omits an option the issue names as part of the trigger (the driver flag on a driver-specific issue), or when there are no steps at all. | required |
| artifact-shows-issue | The report's artifacts (command output, logs, error text, tracebacks, described screenshots), read against the specific behavior the issue describes: the error class and message, exit code, panic, wrong output, or missing output. Also the report's command or input read against the issue's trigger. | Pass when at least one artifact shows the behavior the issue names (the same error or panic text, the same wrong output or the same absence, on the issue's trigger or an equivalent one), OR the report says up front that it could not reproduce and shows the artifact of what it did observe. A control run is welcome but not required. Fail when (a) there is no artifact, only prose ("I can confirm", "it happens every time"); (b) the artifact shows only setup and not the symptom (a version banner, a session list, "the tabs are visible"); (c) the artifact shows a different behavior than the issue describes (a graceful argument-validation error where the issue reports a panic or abort, a compile error where the issue reports a runtime path error, a parse error where the issue reports a panic, garbled output with the process still alive where the issue reports a crash, an exit code that differs from the one the issue names); or (d) the input or command was changed from the issue's trigger in a way that changes what is tested (a different range syntax, a colon for an equals sign, a changed expression) and the report does not say so. Read the artifact, not the sentence after it: "as you can see, it crashes" is not evidence. | required |
| target-faithful | The environment record's project version, platform, and build, read against what the issue targets: the version the reporter names, any "confirmed on latest / main" statement in the issue or thread, and any platform or build profile the thread says is decisive | Pass when the version tested is the issue's version, a newer release, or the main branch, OR when the tested version, platform, or build differs from the issue's and the report names the difference ("the issue was filed against X; I tested Y", or a cannot-reproduce that lists what differed). Fail when the tested version is older than the version the issue was reported or confirmed on, or the platform or build profile differs in a way the issue or thread says matters, and the report neither names the deviation nor limits its conclusion to what it ran. | required |
| outcome-honest | The report's stated result (its result line, "Actual" line, conclusion, and any confidence or frequency language), read against the artifacts in the same report and against the issue's expected and actual | Pass when the report's central claim (reproduced, confirmed, could not reproduce, cause found) is backed by an artifact shown in the report, expected and actual are stated the same way round as the issue states them, and the conclusion stays within what was run. An honest cannot-reproduce that says so up front, shows what it ran, and names what differed passes. A minor side observation without its own artifact does not fail this check when the central claim is backed. Fail when the central claim outruns the evidence: reproduction or confirmation asserted with no artifact; a root cause asserted with no transcript or artifact showing it ("I verified this race condition"); frequency or breadth claims ("100% reproducible", "on two machines", "ten times") standing in for a missing artifact; "expected" written as the buggy behavior or otherwise backwards from the issue; or a conclusion that generalizes past the run (declaring the bug present on a build or platform the report did not show it on, or one the maintainers said they could not reproduce on). | required |
| claim-specific | The candidate claim comment, read against the issue's title, body, and thread highlights | Pass when the comment names at least one specific of this issue (the symptom in the writer's words, a version, a file or function, a pointer from the thread, what they ran or plan to run) AND states an intent the writer can deliver (investigate, reproduce, test a patch, read a code path, report back). Modesty is not a fail: a claim that reports a failed reproduction attempt and a next step passes. Fail when the comment is a +1 or me-too with no intent, could be pasted unchanged onto any other issue, promises a fix by a date or "guaranteed", or asks for assignment or for the issue to be reserved in place of a concrete plan. | required |
| conventions-respected | The repo facts' `contribution policy` line (CONTRIBUTING.md, AI policy files, templates), read against both the claim comment and the repro report. Course packages count as AI-assisted work. | Pass when the policy line reports no AI statement, OR states conditions the comments meet: (a) if the policy requires disclosing AI use in comments or issues, or "all AI usage in any form", at least one of the two comments discloses that AI assisted and roughly how; (b) if the policy only asks that comments be in the contributor's own words, that the contributor understand and take responsibility for the work, or limits its disclosure ask to pull requests, the comments pass when they read as first-person and specific to this issue (AI-assisted is not AI-generated; a comment a person wrote in their own words satisfies a human-voice rule); (c) a rule against fully AI-generated content with assistive use allowed is a condition, and a first-person comment that owns its steps meets it. Fail when the policy requires disclosure of AI usage that covers issue comments (or all usage in any form) and neither comment discloses, or when the policy bans AI-assisted contributions outright. | required |
| template-followed | The repo facts' `bug reports` template line, read against the repro report's content | Pass when each item the repo's bug-report template asks of a reporter that applies to a reproduction (version, OS, install method, steps, actual, expected, logs, a bounded input) is present somewhere in the report, under any heading or none. Fail when one or more applicable items are absent. This check never changes the verdict; it is a nudge to include what the maintainers will ask for. | preferred |

## Verdict rule

Accept only when every `required` check passes: env-recorded,
steps-rerunnable, artifact-shows-issue, target-faithful, outcome-honest,
claim-specific, and conventions-respected. Any single `required` fail
rejects the package. `unclear` on a `required` check counts as fail:
proof that cannot be verified from the package is proof that is not
ready to post. The `preferred` check (template-followed) never changes
the verdict; report it so the writer can fix it before posting.

In live claim-only mode, the checks that read the repro report
(env-recorded, steps-rerunnable, artifact-shows-issue, target-faithful,
outcome-honest, template-followed) are reported as `unclear` with the
evidence `not yet applicable: claim-only draft` and are left out of the
rule; the verdict then rests on claim-specific and
conventions-respected alone.
